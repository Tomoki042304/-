# 習慣の登録・実行記録

状態：ローカル実装と模擬API試験済み。ユーザーから専用SQLの適用・メタデータ検証成功報告を受領。実API試験97項目成功、一時ユーザー4件と試験データの削除確認済み。今回の機能は未push・未公開。既存データ・Auth設定・既存関数は変更していない。

## 仕様

- 毎日の習慣を複数登録する。習慣名は必須120文字以内、補足は任意1000文字以内。文字数はUnicodeコードポイント単位。
- 状態は「取り組む」「休止中」。休止は習慣や履歴を削除しない。
- 本人のみ閲覧。共有、曜日別スケジュール、数値目標、通知、習慣の削除は今回含めない。
- 日本時間（Asia/Tokyo）の日付で、1習慣につき1日1記録。今日の記録を付け、今日の記録だけを取り消せる。
- 過去や未来への記録・取り消しは提供しない。休止中は新しい実行記録を付けられないが、今日の既存記録の取り消しは可能。
- 一覧は登録日時の新しい順で20件ずつ追加表示。各習慣に今日の実行状態と最近7暦日の実行日・日数を表示する。

習慣名・補足はテキスト描画し、HTMLを実行しない。編集は1件ずつ、入力を破棄する場合はボタンに明示する。会員資格の再確認でも編集入力を保持し、無効・未確認時には描画・保存を行わない。再読み込みやログアウト後の未保存入力は保持しない。

## 日付と通信

画面の日付は端末の日付を日本時間へ変換して求める。30秒ごととフォーカス復帰時に日付を再確認し、変わった場合は履歴を再取得する。日付変化・会員資格の再確認による再取得でも編集入力を消さない。古い一覧リクエストは中断し、新しいリクエストの結果だけを反映する。

DBの記録・取り消し権限は、クライアントの日付を信用せず、CURRENT_TIMESTAMPをAsia/Tokyoへ変換した日付で判定する。端末の時計がずれている場合や、日付切り替えと操作が重なった場合は拒否されることがある。画面の再取得と通信確認を案内し、過去日へ自動で書き直すことはしない。

習慣は固定UUIDでINSERTし、更新はname・note・statusだけのUPDATE。本人ID・習慣ID・取得済みupdated_atを条件にして競合を検出する。保存結果が不明なら同IDで確認してから再保存する。

実行記録はINSERTだけで、UPDATEやUPSERTを使用しない。DB主キー `(habit_id, log_date)` で日ごとの重複を防ぐ。取り消しは本人ID・習慣ID・日付・取得済みcompleted_atを条件にしたDELETEで、別画面で作り直された新しい記録を古い画面から削除しない。

操作中は連打を受け付けない。結果が不明・失敗・更新0件なら自動再送せず、記録ボタンを無効にして「習慣一覧を更新」で実際の状態を再確認する。成功応答を検証した操作だけ成功表示する。成功後の一覧再取得だけが失敗しても、確認済みの結果を画面に保持して一覧エラーを案内する。

履歴は表示対象の習慣IDと本人IDを指定して最近7日だけ取得し、最大20習慣×7日を超えて黙って欠落しないよう取得上限を設ける。習慣と履歴の取得は別APIリクエストであり、同時編集中の完全に同一時点のスナップショットではない。追加表示中に別画面から登録が入ると一覧の重複・取りこぼしが生じる可能性があり、先頭からの一覧更新で読み直す。成功操作後・会員再確認時は先頭ページへ再取得する。

## SQL案

`supabase/proposals/20261027_shidoroku_habits.sql`。自動実行されるmigrationsには置いていない。

| 追加テーブル | 主な項目と制約 |
| --- | --- |
| `shidoroku_habits` | UUID主キー、会員を参照するuser_id、name、note、active / paused、日時。id＋user_idのUNIQUE制約 |
| `shidoroku_habit_logs` | habit_id、user_id、log_date、DBが設定するcompleted_at。主キーはhabit_id＋log_date。habit_id＋user_idの複合外部キーで所有者の整合性を保証 |

- 2テーブルにRLSを有効化。習慣のSELECT / INSERT / UPDATE、記録のSELECT / INSERT / DELETEの計6ポリシー。
- 習慣・履歴のSELECTは有効会員本人のみ。習慣の状態が休止中でも履歴を保持・閲覧できる。
- 記録のINSERTは有効会員本人・取り組む状態の本人習慣・日本時間の今日に限定。DELETEは有効会員本人・今日に限定し、習慣の休止状態では妨げない。
- authenticatedの習慣へのINSERTは指定5列、UPDATEは指定3列。記録へのINSERTは指定3列とDELETEのみ。ログのUPDATE、習慣DELETE、ID・所有者・日時変更、TRUNCATEは許可しない。
- PUBLIC / anonには権限を付与しない。既定の広い権限は新規2テーブルで取り消す。service_roleには専用テーブルのCRUDを付与。
- 既存の専用日時関数を参照するトリガー1件、取得用インデックス2件を追加。既存の関数・テーブル・Auth設定・デフォルト権限は変更しない。

### 適用前確認

対象が `imgearpizizqkutzrpuz` であること、新規テーブル・型・関数・インデックス名に衝突がないこと、専用会員テーブルとgen_random_uuid・承認済みの日時関数が存在することをメタデータで確認する。日時関数のSECURITY INVOKER・空search_path・所有者変更拒否・作成日時保持の定義と、DDLイベントトリガーの干渉がないことも確認する。

ユーザー承認を得てSQL全文を1トランザクションで適用する。失敗した接続はROLLBACKして停止し、自動修正・再適用しない。適用後は2テーブルの構造、主キー・外部キー・CHECK、RLS6件、列権限、トリガー、インデックスをメタデータで確認する。専用テーブル削除による切り戻しはデータを失う可能性があり、保全と別承認なしにDROPしない。
