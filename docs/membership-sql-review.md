# 会員SQL案の確認・適用手順（未実行）

対象ファイル：`supabase/proposals/20261026_shidoroku_membership.sql`。
自動適用を防ぐため、`supabase/migrations` には置いていない。

## この案で追加するもの

- `public.shidoroku_memberships`、`public.shidoroku_profiles`。
- `public.shidoroku_stamp_record()` と、専用2テーブルにだけ付く日時管理トリガー2件。
- 本人用会員行のSELECTポリシー1件と、有効会員の本人用プロフィールのSELECT / INSERT / UPDATEポリシー3件。
- ブラウザ向け権限は必要最小限。プロフィールのUPDATEは表示名だけ。DELETE、TRUNCATE、会員登録・昇格・停止解除は許可しない。
- `service_role` には専用テーブルのCRUDだけ付与。秘密キーの設定や管理APIの作成は含まない。

会員行は自動作成しない。明示的に有効化するまではstatusの既定値は `suspended`。管理者のブラウザも一般会員と同じ制限を受ける。Authユーザー作成トリガー・既存関数の流用はない。

## 適用前に必要な確認

1. 選択先が `imgearpizizqkutzrpuz` であることをツールのプロジェクト指定や管理画面で確認する。DB名だけでは判別できず、このSQL自身にはProject IDを検証する仕組みがない。
2. 新規オブジェクトと同名のテーブル・関数・型などがないこと、権限ロールとAuth参照先が存在することを確認する。プレーンなCREATEで、同名なら上書きせず失敗する。
3. 既存のDDLイベントトリガーと新規オブジェクトの既定権限を確認する。イベントトリガーはテーブル用トリガーとは別物で、今回未確認。自動GRANT・自動RLS設定などがある場合はSQL案と照合する。
4. 対象テーブルに依存する既存オブジェクトがないことを確認し、既存3テーブル・関数・ポリシー・権限のメタデータを比較用に保存する。個人データは取得しない。
5. 共有Authの制約と、既存側の本人用パスに新アプリのJWTでもアクセスできる可能性を確認する。専用RLSは既存側へのアクセス制御を変更しない。
6. `auth.users` から会員行・プロフィールへ連鎖する削除を確認する。既存Authユーザーが運営操作で削除されれば新アプリの専用データも削除される。アプリからAuth削除は提供しない。
7. SQL適用と検証用の合成ユーザー・データ作成について、それぞれ承認を得る。

## 適用時

- SQL案の全体を1トランザクションとして実行する。複数の独立呼び出しに分割しない。
- RLS・REVOKE・GRANTを省略してCREATEだけ実行しない。既定の広い権限があるため、途中状態を公開しない。
- プロジェクトIDと実行結果を記録する。エラー時は接続に残ったトランザクションをROLLBACKする。成功したと推測して再実行しない。
- デフォルト権限・既存テーブル・既存Auth設定は変更しない。

## 切り戻し

失敗したトランザクションはROLLBACK。適用後の専用オブジェクト削除はデータを失うため、別承認と専用データの保全確認が必要。自動DROPやCASCADEでの削除スクリプトは用意していない。既存テーブルやAuthユーザーを削除して切り戻さない。

### 別チャットでの読み取り専用チェック結果

ユーザーから共有された対象 `imgearpizizqkutzrpuz` の取得結果では、次を確認済み。このチャットからDBへ直接問い合わせた結果ではない。適用直前にも対象と衝突を確認する。
