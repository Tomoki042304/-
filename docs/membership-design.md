## 共有Authの境界

Supabase Authのユーザー、メールアドレス、パスワード、プロバイダー設定、メール送信枠は既存アプリと共有する。同じメールアドレスで新規アプリ専用の別Authユーザーを作れるとは想定しない。パスワード変更やAuthユーザー削除は既存アプリにも影響する。

専用テーブルとRLSで新アプリのデータへのアクセスを制限するが、プロジェクト全体を完全には分離できない。調査済みの既存ポリシーには、承認なしでも本人用パスへの書き込みを許すものがある。新アプリのログインで得たJWTにも既存の `authenticated` 向け権限が適用される。新アプリで既存テーブルを呼ばないだけでは、APIへの直接アクセスを防げない。

この既存側への影響は新規テーブルのRLSだけでは解消できない。実会員の登録・ログイン開始前に既存環境の用途とこの共有範囲を確認し、許容できない場合は独立プロジェクトが必要。既存RLSを無断で修正する対応は行わない。

## 新規テーブル案

| テーブル | 主な項目 | 目的 |
| --- | --- | --- |
| `public.shidoroku_memberships` | `user_id uuid`（主キー）、`member_id text`（一意）、`role`（`member` / `admin`）、`status`（`active` / `suspended`）、作成・更新日時 | 新アプリの会員資格と権限 |
| `public.shidoroku_profiles` | `user_id uuid`（主キー）、`display_name text`、作成・更新日時 | 本人用プロフィール |

`memberships.user_id` は `auth.users.id` を参照し、Authユーザー削除時は専用会員行も削除する。プロフィールは会員行を参照し、その削除時に連動削除する。外部キーは実装・適用前に既存Auth削除処理との影響を確認する。アプリからAuthユーザー削除は提供しない。

`role` と `status` はNOT NULLとCHECK制約を設ける。氏名・会員IDなどの長さも制約する。パスワード・秘密キー・メール一覧はこれらのテーブルに保存しない。

会員IDは運営が発行する識別子であり、認証情報としては扱わない。利用者が自分で会員資格・管理者権限を作成、変更することはできない。

## データ権限案

| 操作者 | 会員資格 | プロフィール |
| --- | --- | --- |
| 未ログイン | 拒否 | 拒否 |
| ログイン済み・会員行なし | 拒否 | 拒否 |
| 有効な一般会員 | 自分の会員行のみ参照 | 自分だけ参照・作成・表示名更新 |
| 停止中会員 | 自分の会員行のみ参照（停止の案内用） | 拒否 |
| 有効な管理者のブラウザ | 自分の会員行のみ参照 | 初期段階は一般会員と同じ |

他人のプロフィール・会員一覧は初期段階で公開しない。交流機能の公開プロフィールは後から別途設計する。

- 専用テーブルにRLSを有効化し、所有者 `auth.uid()` と新アプリ専用の有効会員資格をDB側で検証する。
- 会員行は本人のSELECTだけ許す。ブラウザからのINSERT / UPDATE / DELETEは管理者を含め禁止する。
- プロフィールのINSERT / UPDATEにはUSING・WITH CHECKと列単位のGRANTを組み合わせ、本人IDの変更を拒否する。更新可能な列は表示名だけとし、日時はDB側で管理する。
- 既存の `is_host()`、`is_member()`、`is_approved()` は流用しない。
- SELECTのない更新や、本人の識別子を差し替える操作も拒否されることを確認する。
- 既定の広い権限を引き継がない。新規テーブルの作成、RLS有効化、PUBLIC / anon / authenticatedの不要権限取消、必要なGRANTを一つのトランザクションで適用する。
- TRUNCATE、REFERENCES、TRIGGERなどをブラウザ用ロールに付与しない。既存のデフォルト権限や既存テーブルのGRANTは変更しない。

## ログインと運営操作

初期案は運営登録制のメールアドレス＋パスワード認証。一般向けの会員登録画面は設けない。独自IDだけでのログインや、ブラウザへの共通管理パスワード埋め込みは行わない。会員IDでのログインが必要なら、別途サーバー側の安全な照合方式を設計する。

初期パスワードの共通化・平文保存を避け、本人がパスワードを設定する招待方式を優先する。ただし共有Authの招待・パスワード再設定、無料メール送信枠、配送可否、リダイレクトは未検証であり、実装前に確認する。既存ユーザーを新規扱いして再招待・パスワード上書きしない。

最初の管理者は運営の明示的な承認を受けてサーバー側から登録する。「最初にログインした人を管理者にする」処理は設けない。初期段階の会員追加・停止・権限変更は、運営承認を受けた操作として扱い、管理画面は後続工程にする。

管理用APIを設ける場合は、Supabase Edge Functionsなどのサーバー側でJWTを検証し、DBの最新の専用会員行から `active` と `admin` を再確認する。ブラウザが送ったrole、user_metadata、表示名などで管理者判定しない。サーバー専用の秘密キーはフロントエンド・VITE変数へ置かず、操作履歴を設計する。導入前に無料枠・費用と権限を確認する。

Authユーザー作成トリガーは追加しない。Auth登録だけでは志動録の会員にならない。停止は専用会員行のstatus変更で行い、共有Authユーザーの削除・停止・パスワード変更を代用しない。停止後は既存セッションがあっても専用RLSでデータ操作を拒否する。共有Authや既存アプリの利用までは停止しない。

ログイン状態維持は専用storageKeyを維持して実装し、現在無効なセッション保存・自動更新・URLトークン処理を、承認されたログイン工程で必要な範囲だけ変更する。storageKeyはブラウザ保存先の区別であり、サーバー側の権限分離ではない。

## 実装・検証の順序

1. この設計と共有Authの制約を確認する。
2. 専用2テーブル・RLS・権限のマイグレーション案をファイルに作成する。SQLの適用は別承認。
3. 検証方法を用意する。実行環境に応じたDBテストに加え、合成ユーザーによるAPI検証を行う。合成Authユーザー作成にも別承認を得る。
4. 未ログイン、非会員、本人、他人、有効管理者、停止会員の読み書き・昇格拒否・所有者変更拒否を確認する。停止済みセッションの拒否も検証する。
5. 既存テーブル・ポリシー・関数の定義が変わっていないことを確認する。実データをコピーしない。
6. 運営承認後に会員登録・ログイン・パスワード設定を実装し、公開前に認証・メール・RLSを検証する。

マイグレーションは追加対象を明示して記録する。同名オブジェクトがあれば上書きせず停止する。失敗時はトランザクションを戻す。適用後の削除による切り戻しは新規データを失う可能性があるため、実行前に専用データの保全方法と承認を確認する。既存テーブルをDROP / TRUNCATE / RESETしない。

GitHubへのpushはCloudflareの自動公開につながるため、DB適用とは別に承認を得る。
