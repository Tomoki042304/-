# 夢・目標の登録・編集

状態：専用SQLの適用成功報告を受領し、実API・RLS試験61項目が成功。ユーザー承認を受けてコミット `2e061ee` をGitHub mainへpushし、Cloudflareのデプロイ成功報告を受領した。続いて公開画面から実APIを使う22項目の試験が成功。各試験の合成ユーザーと専用データは削除確認済み。

## 仕様

- 本人だけが閲覧する目標を複数登録できる。
- タイトル：必須、120文字以内。補足：任意、2000文字以内で改行可能。
- 目標日：任意。日付として扱い、タイムゾーンで前日・翌日へ変換しない。過去の日付も許す。西暦0001～9999年の実在日付に限定する。
- 状態：「取り組み中」「達成」。達成後に取り組み中へ戻すことも可能。
- 一覧は登録日時の新しい順、同一時刻はID順。20件ずつ表示し、「目標をさらに表示」で追加取得する。
- 削除、公開共有、階層化、達成履歴、通知は今回含めない。

一覧から1件ずつ編集する。編集中は別の目標の編集・追加を開始できない。未保存の入力を閉じる場合は「入力を破棄して閉じる」と明示する。会員資格の再確認で表示が閉じても、このコンポーネント内の入力は維持する。再読み込みやログアウトで未保存入力は失われる。

## 保存と復旧

新規目標は編集開始時にUUIDを生成し、その編集が完了するまで同じIDを使う。初回はINSERT、更新は編集可能な4項目だけのUPDATE。UPDATEの条件は本人ID・目標ID・最後に取得したupdated_at。所有者・ID・日時は更新しない。UPSERTや自動の書き込み再試行は行わない。

保存結果が不明・失敗・更新0件なら成功表示を出さず入力を保持する。「この目標の保存内容を確認」で本人とIDを限定して取得し直してから再保存する。初回INSERTがDBでは確定して応答だけ失われた場合、同じIDを読み直して以降はUPDATEするため、復旧操作で重複目標を作らない。既存行が見つからない場合は更新を許可しない。

保存成功後は返された本人の行・ID・編集値を検証してから成功表示し、一覧を先頭ページから読み直す。新規登録や更新が多い状況では、ページ番号方式の追加取得中に他の画面からの新規登録によって重複・取りこぼしが生じる可能性がある。「目標一覧を更新」で先頭から再取得できる。追加表示では同じIDを重複描画しないが、一覧がリアルタイムで完全なスナップショットになる保証はしない。

目標一覧や編集欄の障害は、プロフィール・志言の保存を妨げない。保存内容・補足はReactのテキスト描画を使い、HTMLを実行しない。

## 専用SQL案

`supabase/proposals/20261027_shidoroku_goals.sql`。自動適用のmigrationsには置かない。

- `public.shidoroku_goals`：UUID主キー、専用会員行を参照するuser_id、タイトル、補足、目標日、状態、作成・更新日時。
- 本人の登録順取得用に `(user_id, created_at DESC, id ASC)` インデックスを追加。
- 有効会員本人に限定したSELECT / INSERT / UPDATEのRLS3件。
- 既定の広い権限を新規テーブルで取り消す。authenticatedはSELECTと指定列のINSERT / UPDATEのみ。anon・PUBLICは権限なし。service_roleはCRUD。
- INSERTでは復旧用の固定UUIDを指定できる。UPDATEではID・user_id・日時を変更できず、DELETE / TRUNCATEも許可しない。
- 既存の専用日時関数 `public.shidoroku_stamp_record()` を参照するトリガー1件。関数は変更・置換しない。

追加は1トランザクションで行い、既存テーブル・関数・Auth設定・デフォルト権限は変更しない。エラー時はROLLBACKして停止する。適用後のDROPは専用データを失う可能性があるため、保全・別承認なしには行わない。

### 適用前に確認するもの

1. 対象がテスト環境 `imgearpizizqkutzrpuz` であること。SQL内のDB名からProject IDを推測しない。
2. 新規テーブル名と同名のテーブル・ビュー・型・関数がなく、インデックス名の衝突もないこと。
3. 専用会員テーブル、承認済みの日時関数、`pg_catalog.gen_random_uuid()` が存在すること。関数を呼び出す必要はなくメタデータで確認する。
4. 日時関数がSECURITY INVOKER・空search_path・所有者変更拒否・作成日時保持の承認済み定義で、適用者にトリガー作成権限があること。
5. DDLイベントトリガーが今回のRLS・権限設定に干渉しないこと。
6. SQL適用についてユーザー承認を得てから実行すること。

適用後は構造、制約、RLS、ポリシー、列権限、インデックス、トリガーをメタデータで確認する。実データによる試験は合成ユーザー・目標データの作成と終了後の削除に別承認を得る。
